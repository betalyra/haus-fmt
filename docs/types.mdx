Data never imports anything. `Date("2027-03-15")` and `Money(19.90, EUR)` are valid haus with a schema or without one: to a parser, each is just a tag with its arguments. Imports only appear in schema files, and they bring types, not rules: every schema binding checks the rules of the prelude and `std/time`, and a package adds none until your application adds its codecs ([What haus checks](/docs/checks)).

```haus title="workshop.haus"
{
  signupBy: Date("2027-03-15"),
  price: Money(19.90, EUR),
  seats: 40,
}
```

```haus-schema title="workshop.schema.haus"
import std/time (Date)
import @haus-fmt/money (Money)

type Root = { signupBy: Date, price: Money, seats: UInt16 }
```

`UInt16` comes from the prelude, `Date` from a standard module, and `Money` from a schema package.

| | Prelude | Standard modules | Packages |
|---|---|---|---|
| Examples | `Int`, `String`, `Decimal`, `Maybe a` | `Date`, `Instant`, `Duration` | `Money`, `LatLng`, your own |
| In a schema | nothing: always in scope | `import std/time (Date)` | `import @haus-fmt/money (Money)` |
| Defined by | the spec | the spec | package authors: `@haus-fmt/` for the official extensions, anyone else under a name they own |
| Versions | fixed from haus 1.0 on | versioned with the spec; a module only gains types | its own semantic version |
| Comes with every schema binding | yes | yes | no: you add it as a dependency, from npm, crates.io, PyPI, … |
| Rules beyond the shape | built in: integer ranges, exact decimals | built in: the [std/time profile](/docs/spec/time) | none in the schema; profiles, checked where you add their codecs |
| Your schema can define a type with the same name | no | yes, if it doesn't import it | yes, if it doesn't import it |

## The prelude

The prelude is always in scope. It is the data model itself:

- **Numbers:** `Int` (any size), `Int8`, `Int16`, `Int32`, `Int64`, `UInt8`, `UInt16`, `UInt32`, `UInt64`, `Float32`, `Float64`, `Decimal`
- **Text and bytes:** `String`, `Bytes`
- **Structure:** `Bool`, `Maybe a`, `Result e a`, `Array a`, `Map v`, and records `{ … }`
- **Anything:** `Any`, a value kept exactly as parsed, for a payload you pass on without knowing its shape
- **Secrets:** `Secret a`, the same data as `a`, kept out of logs and error messages
- **Streams:** `Stream a`, a whole file as a sequence of values

Their rules are built in: `300` is out of range for a `UInt8`, and a `Decimal` keeps `19.90` as `19.90`. Prelude names are reserved, so a schema can't define its own `String` or `Int`. The full list, with comments: [`prelude.schema.haus`](https://github.com/betalyra/haus-fmt/blob/main/spec/prelude.schema.haus).

## Standard modules

Standard modules ship with the spec, and every schema binding supports them completely. Today there is one, `std/time`:

```haus-schema
import std/time (Date, Time, DateTime, Instant, ZonedDateTime, Duration, YearMonth, TimeZone)
```

Each value is a tag around a string. A schema binding checks the string against the [std/time profile](/docs/spec/time): with `Date` in the schema, `Date("2027-02-30")` is an error, not a date. Which type fits what is in [Time and money](/docs/tours/time-money).

A module only gains types and its rules never change, so an import of a standard module carries no version.

Forget the import and the checker tells you what to write. Your editor shows it as you type:

```text
unknown type Date; import it with: import std/time (Date)
```

## Schema packages

Everything else is a schema package: an ordinary schema file, `schema.haus`, with a manifest next to it, installed like any other dependency. A package fixes the shape only and changes no syntax.

### Official extensions

| Package | Types | Profile |
|---|---|---|
| [`@haus-fmt/money`](https://github.com/betalyra/haus-fmt/tree/main/extensions/money) | `Money`, `Currency` | `iso`: currency codes are three letters A–Z |
| [`@haus-fmt/geo`](https://github.com/betalyra/haus-fmt/tree/main/extensions/geo) | `LatLng`, `BBox` | `wgs84`: latitude and longitude in range |

The schema says a `Money` is a `Decimal` and a currency tag. Which tags count as currencies has more than one answer (ISO 4217, your shop's list, crypto currencies), so the schema doesn't decide it. A profile is one answer: a definition of the type, written as a rule in prose, which test vectors test. Your application picks one by adding its codec; until then, `Money(19.90, Xyz)` decodes. Like `std/time`, each official profile has a reference checker in Lean, and the codecs of every binding that ships them are fuzzed against that checker in CI (the table below).

An import can name the major version it expects: `import @haus-fmt/money@1 (Money)`.

### Your own packages

Anyone can publish a schema package. A package is a directory with two files: a manifest, `package.haus`, and its schema, `schema.haus`:

```haus title="package.haus"
{ name: "@acme/shipping", version: "1.0.0" }
```

A package is one schema file. It imports other packages by name, never files.

- The name is lowercase, `@org/name`.
- The version in `package.haus` is the version you publish. It must equal the one in `package.json` or `Cargo.toml`, so release them together.
- `package.haus` and `schema.haus` are plain files, not symbolic links (the package's folder may be one).
- A package imports only the packages it declares as dependencies. On npm, declare them as `peerDependencies`: npm then installs one copy for the whole application. A build that reaches two versions of one package stops with `duplicate-package` and names both, rather than picking one.

There is no haus registry. Publish wherever your users install dependencies from: npm, crates.io, PyPI, a private registry or a git repository. Name the package after something you own (`@your-domain/…`, `@your-github-org/…`), and give it no install scripts: a schema package is data. Names, resolution and versions are in [spec §13.3](/docs/spec#133-schema-packages).

For types shared within one project, you don't need a package: `import ./common (Address)` imports `common.schema.haus` from the same folder. Relative imports are for your own files: a package is imported by its name, never by a path into its folder.

## Host types in each language

What a value becomes in your code. Every default keeps the value exactly: encoding what was decoded gives back an equal value. The choices marked as lossy keep less, and their documentation says what they drop.

### The prelude

| | `Int` | `Int8` … `UInt64` | `Decimal` | `Bytes` | `Maybe a` |
|---|---|---|---|---|---|
| TypeScript | `bigint` | `number`; `bigint` for `Int64`, `UInt64` | `string`, the exact literal | `Uint8Array` | `h.Maybe<A>` |
| Effect | `bigint` | `number`; `bigint` for `Int64`, `UInt64` | `string`, the exact literal; `BigDecimal` with `Haus.DecimalAsBigDecimal` (lossy) | `Uint8Array` | `Option<A>` |
| Rust | `haus::Int` | `i8` … `u64` | `haus::Decimal`, the exact literal | `haus::Bytes` | `Option<A>` |
| Python | `int` | `int` | `str`, the exact literal; `decimal.Decimal` with `DecimalCodec` (lossy) | `bytes` | `Some(x)`, `Nothing()` |
| Go | `haus.Number`, the literal (`BigInt()` for a `*big.Int`) | `haus.Number` | `haus.Number`, the literal | `haus.Bytes` | the `haus.Variant` |
| Swift | `HausNumber`, or a fixed-width integer | `Int8` … `UInt64`, or any fixed-width integer | `HausNumber`, the exact literal | `[UInt8]` | `Optional` |
| JVM | `BigInteger`, `long`, `int`, … | `long`, `int`, `short`, `byte`, `BigInteger` | `Value.Number`, the exact literal; `BigDecimal` (lossy) | `byte[]` | `Optional<A>`, or `null` |
| Roc | `Int`, the exact digits | `I8` … `U64` | `Str`, the exact literal | `List(U8)` | `[None, Some(a)]` |
| Zig | `Decoded` | `Decoded` | `Decoded` | `Decoded` | `Decoded` |

Go decodes to checked `haus.Value`s (`schema.DecodeAs` gives a codec's host type), and Zig to its own `Decoded`, which keeps every value. In Swift and on the JVM, you choose among the listed types when you write your `Codable` types or records; a value that doesn't fit is `out-of-range`.

### std/time and the official packages

| | std/time | std/time, other host types | `@haus-fmt/money` (`iso`), `@haus-fmt/geo` (`wgs84`) |
|---|---|---|---|
| TypeScript | `string`, the checked text | `h.InstantAsDate`: a `Date`, in `h.*` schemas (lossy) | `iso`, `wgs84`: the same values, checked |
| Effect | `string`, the checked text | `Haus.InstantAsDateTime`, `Haus.ZonedDateTimeAsDateTime`: `DateTime` (lossy) | `iso`, `wgs84` from `./effect`: the same values, checked |
| Rust | `haus::time::Date`, …: the checked text | a codec of your own (to `jiff`, say) | `Iso` → `IsoMoney`, `IsoCurrency` → `CurrencyCode`, `Wgs84` → `Point`, `Wgs84BBox` → `Bounds` |
| Python | `str`, the checked text | `DateCodec` → `datetime.date`, `InstantCodec` → `datetime.datetime` (lossy) | `haus_money.iso`, `haus_geo.wgs84`: the same values, a currency as `"EUR"` |
| Go | the checked `haus.Value` | `schema.InstantTime` → `time.Time` (lossy) | `money.Iso` → `money.Money`, `geo.Wgs84` → `geo.LatLng`, `geo.Wgs84BBox` → `geo.BBox` |
| Swift | `String`, the checked text | a `HausCodec` of your own (Foundation's `Date`, say) | none yet |
| JVM | `String`, the checked text | `LocalDate`, `YearMonth`, `LocalTime`, `LocalDateTime`, `Instant`, `OffsetDateTime`, `ZoneId` (lossy) | `MoneyCodecs.ISO` → `Money`, `GeoCodecs.WGS84` → `LatLng`, `WGS84_BBOX` → `BBox` |
| Roc | `Str`, the checked text | a codec module of your own | `Iso` → `{ amount : Str, currency : Str }`, `Wgs84` → `{ lat : F64, lng : F64 }`, `Wgs84BBox` |
| Zig | `Decoded` | none: no codecs yet | none yet |

Without a codec, a package's type decodes like any type of its schema: a `Money` is a variant with a `Decimal` and a tag, and a currency of `Xyz` passes. Codecs for JavaScript's Temporal are planned after 1.0.

## Why three?

**Why isn't time in the prelude?** Prelude names are reserved in every schema. With `Time` in the prelude, a schema that has its own `Time` type would have to rename it. In a module, a name is only taken when you import it. And from 1.0 on, the prelude is fixed: new built-in types only go into modules, so no existing schema ever breaks.

**Why is time a standard module, and money a package?** The tiers differ in who checks a type's rule. Every schema binding checks the rules of `std/time`, always, and they never change. A package's rule is checked where your application adds its codec, and can change with a major version of the package. A type goes into a standard module only when its rule has one definition that everyone shares, nearly every domain needs it, and its rule must be on everywhere. Time passes: `2027-02-30` is no date anywhere, and a service that let it through would disagree with the others about what the data says. Money doesn't: which codes are currencies has several legitimate answers, so each is a profile and your application picks one, and `Decimal` already keeps amounts exact. Coordinates have one definition but few domains need them. The rules are in [spec §13.2](/docs/spec#132-standard-modules), and in plain words in [What haus checks](/docs/checks).

**Can a package become a standard module later?** Your data wouldn't notice: it never names where a type comes from, and a schema would change an import line. Your code would: codecs and generated code refer to a type by its id (`@haus-fmt/money@1#Money`), which names its package. So when in doubt, a type is a package.

**Why can't a schema say "at most 100"?** Because that is your application's rule, not part of what a number is. Where such rules go: [What haus checks and what it doesn't](/docs/checks).
