Your paging tool from the [tour](/docs/tour) now has a mobile app too. The server updates daily, the app whenever people install the update. Both read `team.haus`.

<Story>

<Step lang="haus-schema" label="team.schema.haus" code={steps[0]}>

### Two apps, one file

Both apps read the team with this schema. Records and variants are **open** unless you say otherwise.

</Step>

<Step label="team.haus" code={steps[1]}>

### The server needs time zones

It starts writing `timezone`. The old app has never heard of it and doesn't care: open records **ignore fields they don't list**.

</Step>

<Step label="team.haus" code={steps[2]}>

### Alan moved to Teams

The old app doesn't know `Teams`. It doesn't crash: it reads it as **Unknown**, keeps the raw data, and can show "unsupported contact".

</Step>

<Step label="team.haus" code={steps[3]}>

### The old app saves the file

Ada changes her email in the old app, and it writes the team back. It decoded the file with its schema, so what it writes is what that schema lists: Ada's `timezone` is **gone**. Alan's `Teams` contact survives, because an Unknown value is written back as it was read.

A program that edits a file it doesn't fully know should change the values parsed without a schema, not the decoded ones, or keep the parts it doesn't own as `Any`. Where losing a field is worse than failing, a `closed` record makes an unknown field an error instead.

</Step>

<Step lang="haus-schema" label="team.schema.haus" code={steps[4]}>

### Catch the schema up

Add the new tag, and the new field as optional. Both are **minor** changes: a file that uses only the fields and tags the old schema listed reads the same under the new one.

A field the schema doesn't list is kept free for its later versions. The server used `timezone` before the schema had it; that worked only because the schema then gave it the type the server wrote. Had it written `timezone: 2`, the old schema would have accepted that file, and the new one would reject it.

</Step>

<Step lang="haus-schema" label="team.schema.haus" code={steps[5]}>

### Some cases must not be guessed

An app that doesn't understand a status shouldn't page someone anyway. `closed` makes an unknown status an **error**.

The price: adding `Sick` later is a breaking change. That's the point.

</Step>

<Step lang="haus-schema" label="team.schema.haus" code={steps[6]}>

### Renaming without breaking

Renaming `name` would break every reader. Instead, add `displayName` next to it, move everyone over, and drop `name` in the next major version.

</Step>

<Step lang="haus-schema" label="team.schema.haus" code={steps[7]}>

### Say what's going away

`@deprecated("use displayName")` tells everyone while they move. Editors mark `name` with a hint wherever the data uses it, and generated code carries the language's marker: `#[deprecated]` in Rust, `@deprecated` in TypeScript.

Reading and writing don't change: an attribute never changes what a schema accepts, so adding one is a **patch** change.

</Step>

</Story>

## Cheat sheet

| Change | Kind | Older readers |
|---|---|---|
| New optional field in an open record | minor | ignore it |
| New tag in an open variant | minor | read it as Unknown |
| New type | minor | don't see it |
| Rename or remove a field or tag | major | break |
| Change a field's type | major | break |
| Make a type `closed` | major | break on anything new |
| Mark a type, field or tag `@deprecated` | patch | read it as before |

An older reader that writes the data back drops the new fields: it writes what its schema lists. Unknown tags are written back as they were read.
