# haus for Roc

Built against the Roc nightly compiler (2026-11-03) and basic-cli 0.26.0.

| Path | Contents |
|---|---|
| [`package/`](package) | The haus package: `Value` (data model and parser), `Decode`, `Encode` (compact writer), `Int` (integers of any size), `Streaming` (reads a stream chunk by chunk), `Time` (the std/time profile), `JsonValue`, `FromJson`, `ToJson` (JSON, spec §16) |
| [`examples/`](examples) | The same examples as in TypeScript and Rust, on the same files in [`../examples`](../examples), plus `shop`, a Roc showcase |
| [`schema-test/`](schema-test) | Generated: the schema conformance suite ([`../test-suite/schema`](../test-suite/schema)) as Roc tests |
| [`json-test/`](json-test) | Generated: the JSON suite ([`../test-suite/json`](../test-suite/json)) as Roc tests |

## Examples

| Example | Shows |
|---|---|
| [`quickstart`](examples/quickstart) | `thread.haus`: typed data, decoding, encoding, errors |
| [`order`](examples/order) | `order.haus`: schema packages (`@haus-fmt/money`, `@haus-fmt/geo`) and codecs |
| [`logs`](examples/logs) | `logs.haus`: a stream, read chunk by chunk and written back |
| [`shop`](examples/shop) | Roc's structural types: handlers for any union or record with certain tags or fields (row polymorphism) |

Run each from its folder, because the examples read the shared files by relative path:

```sh
cd examples/quickstart && roc main.roc
cd examples/order && roc main.roc
cd examples/logs && roc main.roc
```

## Generated modules

Each example's types and decoders come from its schema, like in TypeScript
(content mapper) and Rust (`haus-fmt-build`). Roc has no build scripts, so the
modules are generated by `haus-gen` and checked in, like protobuf output:

| Schema | Module |
|---|---|
| `thread.schema.haus` | [`quickstart/Thread.roc`](examples/quickstart/Thread.roc) |
| `logs.schema.haus` | [`logs/Logs.roc`](examples/logs/Logs.roc) |
| `order.schema.haus` | [`order/Order.roc`](examples/order/Order.roc), and [`order/Typed.roc`](examples/order/Typed.roc) with codecs |
| `@haus-fmt/money`, `@haus-fmt/geo` | [`HausFmtMoney.roc`](../extensions/money/roc/HausFmtMoney.roc), [`HausFmtGeo.roc`](../extensions/geo/roc/HausFmtGeo.roc): Roc packages next to the npm and Cargo ones |

After changing a schema, regenerate them (`haus-gen` is part of
[`haus-fmt-build`](../rust/haus-build), so this needs Rust):

```sh
examples/gen.sh
```

| haus | Roc |
|---|---|
| `{ a: T, b?: U }` | `{ a : T, b : [Missing, Present(U)] }` |
| `< A \| B T \| C { … } >` | `[A, B(T), C({ … }), Unknown(Str, List(Value))]`, without `Unknown` when closed |
| `Maybe a`, `Result e a` | `[None, Some(a)]`, `Try(a, e)` |
| `Array a`, `Map v` | `List(a)`, `List((Str, v))` |
| `Int`, `Int8`…`UInt64`, `Float32`, `Float64` | `Int`, `I8`…`U64`, `F32`, `F64` |
| `Decimal`, `Date`, `Instant`, … | `Str`: exact text, std/time checked by its profile |
| `< >` | `[Bare(Str), Other(Str, List(Value))]`: any variant, kept as it was |
| `type Pair a = …` | `Pair(a)`, decoded with `decode_pair(v, decode_a)` |
| `Any` | `Value`: any value, as parsed |
| `Secret a` | `Secret(a)`: `Str.inspect` and `dbg` show `<redacted>`; `.expose()` gives the value |
| `@deprecated("why")` | a `## Deprecated…: why` line in the type's doc comment (Roc has no deprecation marker) |

Named variants are nominal (`:=`), and so are records that refer to
themselves (`Tree := { name : Str, children : List(Tree) }`). A type named
like a Roc builtin or an imported module gets a `_` in Roc (`type List a`
is `List_(a)`, `type F64 = Float64` is `F64_`); its functions keep their
names (`decode_list`).

A `Secret` is written in full when encoded, but a decode error inside it names
only its place and type (`.pin: not a valid Secret Int (the value is hidden)`).

`Encode.to_str` (and `Encode.stream`) check what they write, so they return
a `Try(Str, Encode.Error)`. What a generated encoder gives is always fine;
what can fail is a `Value` built in code, the raw value of an `Any` or an
unknown variant (spec §9.8): `Num("abc")` is an error (`.extra: not a number
literal`), as are a tag that isn't a tag name, a key used twice in a record,
and nesting, strings and numbers beyond the parser's limits. Number literals
are written as the parser reads them (`Num("1E5")` as `1e5`).
`Encode.message(e)` gives the error with its path.

A float is written in one spelling (spec §15): the fewest digits that read
back as the same `F64` or `F32`, laid out like JavaScript (`0.1`, `1e21`,
`1.5e-7`, `-0`). A number too large for the type is a decode error.

`Int` (the package's `Int` module) is an integer of any size, kept as its digits
and written back unchanged, like `haus::Int` in Rust. `to_i64` / `to_i128` convert
it and fail with `OutOfRange` when it doesn't fit. For a native integer that must
fit, the schema says `Int64` (out of range is a decode error).

A codec is a Roc module with a `Target` type, `decode : Base -> Try(Target, Str)`
and `encode : Target -> Base` ([`Cents.roc`](examples/order/Cents.roc)), chosen
with `--codec ID=MODULE` when generating.

## Streams

`Streaming` reads a stream (spec §6) chunk by chunk and does no I/O: push
bytes split anywhere and get every value whose comma has arrived; memory
holds the current value, not the stream. See [`logs`](examples/logs).

```roc
var $reader = Streaming.reader(Streaming.defaults)
(next, values) = Streaming.push($reader, chunk)?
$reader = next
# …
last = Streaming.finish($reader)?
```

`Streaming.Options` has the parser's `limits`, `max_value_length` (64 Mi
characters) and `require_terminator`. (The module isn't called `Stream`
because Roc has a builtin `Stream`, which hides a package module of that name
from the package's other modules.)

## Canonical form and hashing

`Encode.canonical(v)` is the canonical form (spec §12), `Encode.equals` and
`Encode.compare` use it. `Encode.hash(v)` is the SHA-256 digest of the
canonical form as 64 lowercase hex digits, and `Encode.hash_all(values)` the
hash of a list, such as a file or a stream: the canonical forms joined by `,`
(`hash_all([v]) == hash(v)`). Both use Roc's builtin `Crypto.SHA256`.
`Encode.HashAll` hashes a list as it grows, e.g. a stream while it is read:

```roc
var $hash = Encode.HashAll.empty
for value in values {
    $hash = $hash.add(value)
}
$hash.digest() # == Encode.hash_all(values)
```

(It isn't called `Hasher`, as in TypeScript and Rust, because Roc has a
builtin `Hasher`.)

## Limits

The parser enforces the limits of spec §7. The reading functions use the
defaults (`Value.default_limits`: depth 256, number literals of 1000
characters, exponents up to 6144, strings, record keys and tags of 16 Mi
characters); each has a `_with` version that takes a `Value.Limits` record:

```roc
limits = { ..Value.default_limits, max_depth: 64 }
Value.parse_all_with(text, limits)
```

| Reading | With limits |
|---|---|
| haus text | `Value.parse_all_with`, `Value.parse_with`, `Value.parse_bytes_with`, `Decode.all_with`, `Decode.one_with` |
| a stream | `Streaming.reader({ ..Streaming.defaults, limits })` |
| JSON | `JsonValue.parse_with`, `JsonValue.lines_with`, `JsonValue.from_json_with`, `JsonValue.from_lossless_json_with`, `FromJson.one_with`, `FromJson.lines_with` |
| writing haus for such a reader | `Encode.to_str_with`, `Encode.stream_with` |
| writing JSON for such a reader | `JsonValue.to_str_with`, `JsonValue.write_lines_with`, `JsonValue.to_lossless_json_with`, `JsonValue.lossless_with`, `ToJson.to_str_with`, `ToJson.lines_with` |

`Value.max_supported_depth` is 1024: the parser, decoding, encoding and the
JSON mappings recurse once per level of nesting, so the binding supports no
deeper limit. Every function above fails, before reading or writing anything,
if `max_depth` is larger, with an error that names the maximum (`max_depth
2000 is more than the supported maximum, 1024`); `Value.check_limits(limits)`
says so too. With basic-cli 0.26 a program overflows its stack only past about
24,000 levels on the deepest path (the lossless JSON form of nested variants,
measured on aarch64 macOS, optimized and dev builds alike), so 1024 leaves a
wide margin; the canonical form, the hash and `Encode.equals` take no limits
and recurse further still (about 70,000 levels).

A generated `from_json_<name>` checks the depth of what it read against 256;
for another depth limit, read with `read_json_<name>` and check with
`FromJson.within_limits(result, encode_<name>, limits)`. A generated
`to_json_<name>` doesn't check the depth of the haus value: for a reader with
other limits, write with `ToJson.to_str_with(x, to_json_<name>, limits)`, which
checks the JSON's numbers, strings and nesting (4·d + 1 levels). The canonical
form and the hash don't depend on limits.

## JSON

The two JSON mappings of spec §16. `JsonValue` is a JSON tree (numbers as
text) with a strict reader (I-JSON: no duplicate member names, no unpaired
surrogates, the limits of §7) and a writer. Roc has a builtin `Json`, so the
type is called `JsonValue`.

| | Function |
|---|---|
| JSON without a schema (§16.1) | `JsonValue.from_json(text)`: a `Value` (`null` is `None`) |
| Lossless (§16.2) | `JsonValue.to_lossless_json(value)`, `JsonValue.from_lossless_json(text)` |
| Plain, with a type (§16.3) | `ToJson.to_str(x, to_json_order)`, `FromJson.one(text, from_json_order)` |
| JSON Lines | `ToJson.lines(xs, to_json_order)`, `FromJson.lines(text, from_json_order)` |
| The JSON tree | `JsonValue.parse`, `JsonValue.to_str` |

`haus-gen roc --json` adds `from_json_<name> : JsonValue -> Try(T, Decode.Error)`
and `to_json_<name> : T -> Try(JsonValue, Encode.Error)` to each type, built
from `FromJson` and `ToJson` as decoders are from `Decode` and `Encode`. The
JSON is the same as in Rust and TypeScript: `Int`, `Int64` and `UInt64` as
strings, `Decimal` as a string with its scale, `Bytes` as base64, a closed
variant of tags without payload as a string, other variants as objects with
`"_tag"`. A `Maybe` is `null` or the value when its inner JSON can't be
`null`, and tagged otherwise; Roc has no traits, so haus-gen decides this
from the schema, and a generic type takes a `Bool` for each parameter
(`from_json_pair(j, from_json_a, nullable_a)`).

JSON is opt-in for now: the examples and the schema packages in
[`../extensions`](../extensions) are generated without it, and a module with
JSON needs the packages it imports generated with `--json` too.

A plain JSON text may nest 4·256 + 1 levels, as one haus level can take
several JSON levels, and the value read must then nest at most 256 levels as
a haus value (spec §16). `from_json_<name>` checks that by encoding what it
read (`FromJson.within_depth`); `read_json_<name>`, which the readers of other
types call, doesn't. A generic type's `from_json_pair` doesn't check either,
as it can't encode its parameters: read through a type without parameters
(`type Pairs = Pair Int`).

What Roc can't do yet, or this binding doesn't: a schema package type is
assumed not to be a `Maybe` when deciding whether a `Maybe` of it writes
`null`.

## Tests

```sh
cd package && roc test ConformanceTest.roc && roc test TimeTest.roc
cd package && roc test Decode.roc && roc test Encode.roc && roc test Int.roc && roc test Streaming.roc && roc test Secret.roc && roc test Value.roc
cd package && roc test JsonValue.roc && roc test FromJson.roc && roc test ToJson.roc
cd examples/shop && roc test main.roc
cd schema-test && roc test main.roc
cd json-test && roc test main.roc
```

`ConformanceTest.roc` is generated from `../test-suite` by
`scripts/gen_conformance.py`: for each valid file the values, the canonical
forms, the hash (`.hash`, also computed with `Encode.HashAll` on the values
streamed) and the stream reader giving the same values in chunks of any
size; for each invalid file a rejection, also by the stream reader, whose
error positions after a byte order mark are the whole-file parser's.
`TimeTest.roc` holds the same std/time cases as the TypeScript and Rust
bindings.

[`schema-test/`](schema-test) runs the schema conformance suite
(`../test-suite/schema`, spec §15): `scripts/gen_schema_conformance.py`
generates a module per schema with `haus-gen` (so it needs Rust) and
`SchemaTest.roc` with one `expect` per case. A schema with attributes also
gets a module generated without them (`AttributesBare.roc`), which must give
the same results (attributes don't matter, spec §15). Re-run it after changing
the suite or the generator:

```sh
python3 scripts/gen_schema_conformance.py
```

[`json-test/`](json-test) runs the JSON suite (`../test-suite/json`, spec §16)
the same way: `scripts/gen_json_conformance.py` generates `Plain.roc` for
`plain.schema.haus` with `haus-gen roc --json`, a JSON module for each schema
of the schema suite (they only have to compile), and `JsonTest.roc` with one
`expect` per plain, lossless and schemaless case and per `valid/NAME.json`
(each a lossless case).
