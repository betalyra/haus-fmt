# haus for Roc

Built against the Roc nightly compiler (2026-11-03) and basic-cli 0.26.0.

| Path | Contents |
|---|---|
| [`package/`](package) | The haus package: `Value` (data model and parser), `Decode`, `Encode` (compact and minimised writers), `Int` (integers of any size), `Streaming` (reads a stream chunk by chunk), `Time` (the std/time profile), `JsonValue`, `FromJson`, `ToJson` (JSON, spec §16), `ErrorCode` (error codes, spec §17) |
| [`examples/`](examples) | The same examples as in TypeScript and Rust, on the same files in [`../examples`](../examples), plus `shop`, a Roc showcase |
| [`schema-test/`](schema-test) | Generated: the schema conformance suite ([`../test-suite/schema`](../test-suite/schema)) as Roc tests |
| [`json-test/`](json-test) | Generated: the JSON suite ([`../test-suite/json`](../test-suite/json)) as Roc tests |

## Examples

| Example | Shows |
|---|---|
| [`quickstart`](examples/quickstart) | `thread.haus`: typed data, decoding, encoding, errors |
| [`order`](examples/order) | `order.haus`: schema packages (`@haus-fmt/money`, `@haus-fmt/geo`) and codecs |
| [`logs`](examples/logs) | `logs.haus`: a stream, read chunk by chunk and written back |
| [`shop`](examples/shop) | Roc's structural types: handlers for any union or record with certain tags or fields (row polymorphism) |

Run each from its folder, because the examples read the shared files by relative path:

```sh
cd examples/quickstart && roc main.roc
cd examples/order && roc main.roc
cd examples/logs && roc main.roc
```

## Generated modules

Each example's types and decoders come from its schema, like in TypeScript
(content mapper) and Rust (`haus-fmt-build`). Roc has no build scripts, so the
modules are generated by `haus-gen` and checked in, like protobuf output:

| Schema | Module |
|---|---|
| `thread.schema.haus` | [`quickstart/Thread.roc`](examples/quickstart/Thread.roc) |
| `logs.schema.haus` | [`logs/Logs.roc`](examples/logs/Logs.roc) |
| `order.schema.haus` | [`order/Order.roc`](examples/order/Order.roc), and [`order/Typed.roc`](examples/order/Typed.roc) with codecs |
| `@haus-fmt/money`, `@haus-fmt/geo` | [`HausFmtMoney.roc`](../extensions/money/roc/HausFmtMoney.roc), [`HausFmtGeo.roc`](../extensions/geo/roc/HausFmtGeo.roc): Roc packages next to the npm and Cargo ones |

After changing a schema, regenerate them (`haus-gen` is part of
[`haus-fmt-build`](../rust/haus-build), so this needs Rust):

```sh
examples/gen.sh
```

| haus | Roc |
|---|---|
| `{ a: T, b?: U }` | `{ a : T, b : [Missing, Present(U)] }` |
| `< A \| B T \| C { … } >` | `[A, B(T), C({ … }), Unknown(Str, List(Value))]`, without `Unknown` when closed |
| `Maybe a`, `Result e a` | `[None, Some(a)]`, `Try(a, e)` |
| `Array a`, `Map v` | `List(a)`, `List((Str, v))` |
| `Int`, `Int8`…`UInt64`, `Float32`, `Float64` | `Int`, `I8`…`U64`, `F32`, `F64` |
| `Decimal`, `Date`, `Instant`, … | `Str`: exact text, std/time checked by its profile |
| `< >` | `[Bare(Str), Other(Str, List(Value))]`: any variant, kept as it was |
| `type Pair a = …` | `Pair(a)`, decoded with `decode_pair(v, decode_a)` |
| `Any` | `Value`: any value, as parsed |
| `Secret a` | `Secret(a)`: `Str.inspect` and `dbg` show `<redacted>`; `.expose()` gives the value |
| `@deprecated("why")` | a `## Deprecated…: why` line in the type's doc comment (Roc has no deprecation marker) |

Named variants are nominal (`:=`), and so are records that refer to
themselves (`Tree := { name : Str, children : List(Tree) }`). A type named
like a Roc builtin or an imported module gets a `_` in Roc (`type List a`
is `List_(a)`, `type F64 = Float64` is `F64_`); its functions keep their
names (`decode_list`).

A `Secret` is written in full when encoded, but an error inside it, decoding
or encoding, names only its place and type (`.pin: not a valid Secret Int
(the value is hidden)`), with the code `invalid-secret`.

A generated encoder takes where it is, an `Encode.Encoder`, and gives the
value with the steps it took (`Encode.Encoded(Value)`). `Encode.value` runs
one at the top, for the default limits (`Encode.value_with` for others):

```roc
encoded = Encode.value(comment, Thread.encode_comment)?
text = Encode.to_str(encoded)?
```

A generated decoder, `decode_<name>`, checks first that the value nests at
most 256 levels (spec §9.8): a `Value` built in code isn't limited by a
parser, and decoders recurse once per level, so a deeper one fails with
`nesting-too-deep` at the first container too deep instead of overflowing
the stack. `read_value_<name>` doesn't check: the decoders of other types
call it, and it is what to decode with for other limits,
`Decode.within_limits(value, Thread.read_value_comment, limits)`, or with
`Decode.one_with(text, limits, Thread.read_value_comment)`, as the parser has
checked the depth then. A generic type's decoder doesn't check either.

Encoding counts the values it makes, one step each (spec §9.8): a native
value or a `Value` whose parts are shared (`x = Two(y, y)`, a DAG, which Roc
can't tell from a tree) expands when written out, so encoding fails with
`step-budget` past `limits.max_steps`, 16 Mi by default, as in TypeScript and
Rust. A record's fields and a tag's arguments are encoded one after the
other for that (`Encode.record(e, [("id", Encode.required(u.id, Encode.int)), …])`),
and the writers count the values they write too (`Encode.to_str`,
`JsonValue.to_str`), each value of a stream with a budget of its own.

Decoding a `Value` built in code, and reading a `JsonValue` built in code
(`decode_<name>`, `from_json_<name>`), count its values first, a shared part
each time it is reached, as decoding visits it: past `Value.max_nodes`, 64 Mi
as in TypeScript and Go, they fail with `too-many-nodes` before decoding
anything. Roc has no way to tell a shared part from a copy, so a value that
shares its parts 2^40 times fails only after counting 64 Mi values: some 1.5
seconds in a program built with `--opt=speed`, half a minute in `roc test`.
A parsed value is a tree, no larger than its text.

Encoders and writers check what they build and write (spec §9.8), so they
return a `Try(…, Encode.Error)`. What can fail is a `Value` built in code, the
raw value of an `Any` or an unknown variant: `Num("abc")` is an error
(`.extra: not a number literal`), as are a tag that isn't a tag name, a key
used twice in a record or map, and nesting, strings and numbers beyond the
limits. The encoder checks at each place, so a container fails with
`nesting-too-deep` at the depth limit before its contents are encoded (a
native value nested deeper never recurses past it), and an error inside a
`Secret` says nothing of the value, not even a key of its `Map` or a place in
its `Any`. Encode for the limits you write with: the writer checks again, and
it doesn't know where the secrets are. Number literals are written as the
parser reads them (`Num("1E5")` as `1e5`), integers always in decimal: one
longer than the number limit is `number-too-long`. `Encode.message(e)` gives
the error with its path.

`Encode.to_str` and `Encode.stream` write the compact layout (spec §11), with
spaces: `Person { name: "Ada", age: 36 }`. `Encode.minimised` and
`Encode.stream_minimised` write the minimised layout, the same without the
whitespace between tokens, for the wire and storage:
`Person{name:"Ada",age:36}`. Both check alike, keep the key order, and write
each value on one line (strings escape line breaks and U+2028/U+2029).

A float is written in one spelling (spec §15): the fewest digits that read
back as the same `F64` or `F32`, laid out like JavaScript (`0.1`, `1e21`,
`1.5e-7`, `-0`). A number too large for the type is a decode error.

`Int` (the package's `Int` module) is an integer of any size, kept as its digits
and written back unchanged, like `haus::Int` in Rust. `to_i64` / `to_i128` convert
it and fail with `OutOfRange` when it doesn't fit. For a native integer that must
fit, the schema says `Int64` (out of range is a decode error).

A codec is a Roc module with a `Target` type, `decode : Base -> Try(Target, Str)`
and `encode : Target -> Base` ([`Cents.roc`](examples/order/Cents.roc)), chosen
with `--codec ID=MODULE` when generating; `MODULE` is the app's (`Cents`) or a
package's (`money.Iso`). It applies wherever its type occurs
(spec §13.4), inside packages' types too: the packages' types that contain it,
directly or not, get modules of their own next to `--out` (`OrderAcmeOrders`
for `@acme/orders` and the module `Order`), with the codec applied; the
packages' other types stay their packages' modules' (`AcmeOrders.Customer`).
Give `--package` for every package the schema reaches, so that these modules
can import them ([`closure-test`](closure-test)). A type with a codec of its
own isn't copied: its codec decodes the package's type.

The official profiles (spec §13.3) are codecs of the official Roc packages.
They reject what the profile rejects and keep the value (spec §13.4):

| Package | Codec | For | `Target` |
|---|---|---|---|
| `extensions/money/roc` | `Iso` | `@haus-fmt/money@1#Money` | `{ amount : Str, currency : Str }`: the exact amount, scale kept |
| `extensions/money/roc` | `IsoCurrency` | `@haus-fmt/money@1#Currency` | `Str`: three letters A–Z |
| `extensions/geo/roc` | `Wgs84` | `@haus-fmt/geo@1#LatLng` | `{ lat : F64, lng : F64 }`: the floats as decoded, `-0` kept |
| `extensions/geo/roc` | `Wgs84BBox` | `@haus-fmt/geo@1#BBox` | `{ sw : Wgs84.Target, ne : Wgs84.Target }` |

```sh
haus-gen roc app.schema.haus --module App --out App.roc \
  --package ../extensions/money=money --package ../extensions/geo=geo \
  --codec "@haus-fmt/money@1#Money=money.Iso" --codec "@haus-fmt/money@1#Currency=money.IsoCurrency" \
  --codec "@haus-fmt/geo@1#LatLng=geo.Wgs84" --codec "@haus-fmt/geo@1#BBox=geo.Wgs84BBox"
```

[`profiles-test`](profiles-test) checks them against the profiles' test
vectors, and inside the types of a package that uses the official ones.

## Error codes

Every error has a code (spec §17): a short name for the mistake, such as
`payload-newline` or `missing-field`, the same in every binding. It is a
`code : Str` field next to the message (`reason`) of each error record:

| Error | Fields | Code, for example |
|---|---|---|
| `Value.ParseError` (parser, stream reader, JSON text) | `code`, `reason`, `line`, `column` | `missing-comma`, `null-literal`, `json-syntax` |
| `Decode.Error` (decoding, reading JSON) | `code`, `reason`, `path` | `type-mismatch`, `unknown-tag`, `missing-member` |
| `Encode.Error` (writing haus or JSON) | `code`, `reason`, `path` | `cannot-encode`, `invalid-tag`, `string-too-long` |

```roc
match Value.parse_all("[1 2]") {
    Err(e) => "${e.reason} (${e.code}): ${ErrorCode.hint(e.code)}"
    # "expected ',' or ']', found '2' (missing-comma): Add a comma between the two values."
    Ok(_) => "parsed"
}
```

`ErrorCode` has a constant for each code (`ErrorCode.missing_comma ==
"missing-comma"`), `ErrorCode.all`, `ErrorCode.hint(code)` (the catalogue's
fix), `ErrorCode.category(code)` and `ErrorCode.docs(code)`
(`https://haus-fmt.org/docs/errors#missing-comma`). `Value.error_json`,
`Decode.error_json` and `Encode.error_json` give an error's JSON form:

```json
{"code":"missing-comma","message":"expected ',' or ']', found '2'","line":1,"column":4,"hint":"Add a comma between the two values.","docs":"https://haus-fmt.org/docs/errors#missing-comma"}
```

A decode or encode error has a `path` instead of a line and column, as spec
§15 writes it (`ErrorCode.place`): `$.items[2].price`, a variant's payload
value `i` as `[i]` (`(Money)[1]` in this binding's messages), and the fields
of a record case directly after the case, `$.shape.r` (`.shape(Circle).r`
in messages). A key that isn't an identifier is written as a haus string
in canonical form (spec §12), `["pt-BR"]`, `["a\u{7F}"]`, in both. In a
stream the path starts with the item's index, `$[3].price`. Invalid UTF-8
is reported where it is.

The codes are those of the reference parser and decoder (spec/lean) where a
mistake could be read two ways: a `(` or `{` after a tag without payload on
an earlier line is `payload-newline`, a closing bracket `unexpected-closer`;
`+1` and `.5` are `invalid-number`, `null`, `true` and other lowercase words
`null-literal`, `boolean-literal` and `bare-identifier`; a number is checked
as a literal, then for what follows it, then its length, then its exponent;
for `Bool`, `Maybe`, `Result` and closed variants an unknown tag is
`unknown-tag`, a listed one with the wrong payload `wrong-payload`, and so
is a record case's argument that isn't a record (`Circle(1.5)`, also for
a record case by name, `Wrap(1)` with `Wrap Box`, at the
variant, with the case in the message: "Circle takes one argument, a record"); anything
inside a `Secret` is `invalid-secret`. A codec's error is a `type-mismatch`.

`ErrorCode.roc` is partly generated from the catalogue,
[`../spec/errors.haus`](../spec/errors.haus), by
`scripts/gen_error_codes.py` (the part between its markers). A test in
`ConformanceTest.roc` reads the catalogue with this parser and fails when the
module is out of date; the conformance suites check each rejection's code.

## Streams

`Streaming` reads a stream (spec §6) chunk by chunk and does no I/O: push
bytes split anywhere and get every value whose comma has arrived; memory
holds the current value, not the stream. See [`logs`](examples/logs).

```roc
var $reader = Streaming.reader(Streaming.defaults)
(next, values) = Streaming.push($reader, chunk)?
$reader = next
# …
last = Streaming.finish($reader)?
```

`Streaming.Options` has the parser's `limits`, `max_value_length` (64 Mi
characters) and `require_terminator`. (The module isn't called `Stream`
because Roc has a builtin `Stream`, which hides a package module of that name
from the package's other modules.)

## Canonical form and hashing

`Encode.canonical(v)` is the canonical form (spec §12), `Encode.equals` and
`Encode.compare` use it. `Encode.hash(v)` is the SHA-256 digest of the
canonical form as 64 lowercase hex digits, and `Encode.hash_all(values)` the
hash of a list, such as a file or a stream: the canonical forms joined by `,`
(`hash_all([v]) == hash(v)`). Both use Roc's builtin `Crypto.SHA256`. Every
parsed value has a canonical form, whatever the limits it was parsed with: an
integer is written in decimal with all its digits, however long. A `Value`
built in code may not (spec §9.8): nested deeper than
`Value.max_supported_depth` it fails with `nesting-too-deep`, and with more
than `Value.max_nodes` values, a shared part counted each time it is reached
(`x = Arr([y, y])`), with `too-many-nodes`, before anything is written. So
each of them gives a `Try`: `Encode.equals(a, b) == Ok(True)`, and to sort,
`values.sort_with(|a, b| Encode.compare(a, b) ?? Same)`.
`Value.within_bounds(v, max_depth, max_nodes)` is the check they make, for a
value built in code, with your own bounds.

## Threads

The package is pure: it has no mutable state and no effects, so a platform may run it on many threads at once.

## Limits

The parser enforces the limits of spec §7. The reading functions use the
defaults (`Value.default_limits`: depth 256, number literals of 1000
characters, exponents up to 6144, strings, record keys and tags of 16 Mi
characters). A hex literal has at most as many hex digits as keep every
integer within the number limit in decimal: 829 for 1000. Each has a `_with` version that takes a `Value.Limits` record:

```roc
limits = { ..Value.default_limits, max_depth: 64 }
Value.parse_all_with(text, limits)
```

| Reading | With limits |
|---|---|
| haus text | `Value.parse_all_with`, `Value.parse_with`, `Value.parse_bytes_with`, `Decode.all_with`, `Decode.one_with` |
| a stream | `Streaming.reader({ ..Streaming.defaults, limits })` |
| JSON | `JsonValue.parse_with`, `JsonValue.lines_with`, `JsonValue.import_json_with`, `JsonValue.from_haus_json_with`, `JsonValue.from_haus_json_lines_with`, `FromJson.one_with`, `FromJson.lines_with` |
| decoding a `Value` built in code | `Decode.within_limits(value, read_value_<name>, limits)` |
| writing haus for such a reader | `Encode.value_with`, `Encode.to_str_with`, `Encode.stream_with`, `Encode.minimised_with`, `Encode.stream_minimised_with` |
| writing JSON for such a reader | `JsonValue.to_str_with`, `JsonValue.write_lines_with`, `JsonValue.to_haus_json_with`, `JsonValue.to_haus_json_lines_with`, `JsonValue.haus_json_value_with`, `ToJson.to_str_with`, `ToJson.lines_with` |

`Value.max_supported_depth` is 1024: the parser, decoding, encoding and the
JSON mappings recurse once per level of nesting, so the binding supports no
deeper limit. Every function above fails, before reading or writing anything,
if `max_depth` is larger, with an error that names the maximum (`max_depth
2000 is more than the supported maximum, 1024`); `Value.check_limits(limits)`
says so too. With basic-cli 0.26 a program overflows its stack only past about
24,000 levels on the deepest path (the self-describing JSON of nested variants,
measured on aarch64 macOS, optimized and dev builds alike), so 1024 leaves a
wide margin; the canonical form, the hash and `Encode.equals` stop at
`Value.max_supported_depth` too. Encoders stop at the depth limit
however deep a native value is, and decoders and JSON readers at the depth
limit however deep a `Value` or `JsonValue` built in code is; Roc itself
frees a value recursively, so a value nested some hundred thousand levels
deep overflows the stack when it is dropped (about 250,000 links of a list,
150,000 levels of `Arr`, fewer than 140,000 of `Tag("Some", …)` under `roc
test`), whatever haus does with it.

`max_steps` in `Value.Limits` bounds the work of encoding and writing one
value (16 Mi steps by default, `step-budget` past it); parsing and decoding
don't use it. Decoding, the canonical form, the hash and equality take at
most `Value.max_nodes` values (64 Mi, `too-many-nodes` past it).

A generated `from_json_<name>` checks the depth of what it read against 256;
for another depth limit, check with
`FromJson.within_limits(json, read_json_<name>, encode_<name>, limits)`. A generated
`to_json_<name>` takes an `Encode.Encoder` like `encode_<name>` and checks
the haus value's depth as it writes, but not its lengths: `ToJson.to_str(x,
to_json_<name>)` checks the depth and the JSON's numbers and nesting. For a
reader with limits, write with `ToJson.to_str_with(x, to_json_<name>,
encode_<name>, limits)`, which also checks the haus value that
`encode_<name>` gives: its depth, numbers and lengths. Lengths count on that
value, not on the JSON (spec §16, "Limits"), as the readers count them: a
string's characters, not its escapes, and bytes as two characters per byte,
although base64 spells one byte in four. The canonical form and the hash
don't depend on limits.

## JSON

The three JSON forms of spec §16. `JsonValue` is a JSON tree (numbers as
text) with a strict reader (I-JSON: no duplicate member names, no unpaired
surrogates, the limits of §7) and a writer. Roc has a builtin `Json`, so the
type is called `JsonValue`.

| | Function |
|---|---|
| Schema-based, with a type (§16.3) | `ToJson.to_str(x, to_json_order)`, `FromJson.one(text, from_json_order)` |
| Self-describing (§16.2) | `JsonValue.to_haus_json(value)`, `JsonValue.from_haus_json(text)`: `{"_haus":1,"_value":{"_num":"19.90"}}` |
| JSON import (§16.1) | `JsonValue.import_json(text)`: any JSON as a `Value` (`null` is `None`) |
| JSON Lines | `ToJson.lines(xs, to_json_order)`, `FromJson.lines(text, from_json_order)`; `JsonValue.to_haus_json_lines(values)`, `JsonValue.from_haus_json_lines(text)` (an envelope per line) |
| The JSON tree | `JsonValue.parse`, `JsonValue.to_str`; `JsonValue.import_value(json)`; `JsonValue.haus_json_value(value)` and `JsonValue.from_haus_json_value(json)`, a self-describing value without the envelope (as in an `Any`) |

The caller says which form it reads: `from_haus_json` requires the envelope
(`haus-json-form` without it, `haus-json-version` for a `_haus` other than
`1`), and `FromJson` and `import_json` never look for one. Every writer
escapes control characters (C0, DEL, C1), the bidi controls and U+2028 and
U+2029; reading self-describing JSON rejects DEL, C1 and bidi controls raw
(`control-character`, `bidi-control`), the other readers accept them, and
every reader accepts U+2028 and U+2029 raw.

`haus-gen roc --json` adds `from_json_<name> : JsonValue -> Try(T, Decode.Error)`
and `to_json_<name> : T, Encode.Encoder -> Try(Encode.Encoded(JsonValue), Encode.Error)` to each type, built
from `FromJson` and `ToJson` as decoders are from `Decode` and `Encode`. The
JSON is the same as in Rust and TypeScript: `Int`, `Int64` and `UInt64` as
strings, `Decimal` as a string with its scale, `Bytes` as base64, a closed
variant of tags without payload as a string, other variants as objects with
`"_tag"`. A record case (spec §15) has the record's fields beside `"_tag"`
however the record is written: `Wrap Box` with `type Box = { w : Int }` is
`Wrap(Box)` in Roc, the same record as `Wrap({ w : Int })`, and both write
`{"_tag": "Wrap", "w": 1}`; a type parameter is never one (`Ok a`). A `Maybe` is `null` or the value when its inner JSON can't be
`null`, and tagged otherwise; Roc has no traits, so haus-gen decides this
from the schema, and a generic type takes a `Bool` for each parameter
(`from_json_pair(j, from_json_a, nullable_a)`).

JSON is opt-in for now: the examples and the schema packages in
[`../extensions`](../extensions) are generated without it, and a module with
JSON needs the packages it imports generated with `--json` too.

A schema-based JSON text may nest 4·256 + 1 levels, as one haus level can
take several JSON levels, and the value read must then nest at most 256
levels as a haus value (spec §16); a self-describing one a level more, for
the envelope. `from_json_<name>` checks the JSON's depth before reading it
(so JSON built in code nested deeper fails instead of overflowing the
stack), and the haus value's by encoding what it read
(`FromJson.within_depth`); `read_json_<name>`, which the readers of other
types call, doesn't. A generic type's `from_json_pair` doesn't check either,
as it can't encode its parameters: read through a type without parameters
(`type Pairs = Pair Int`).

A record case with a field named `_tag` or `_args` has no schema-based form:
its `to_json_<name>` and `from_json_<name>` fail with `no-json-form` for a
value of that case (`FromJson.no_json_form`, `ToJson.no_json_form`).

What Roc can't do yet, or this binding doesn't: a schema package type is
assumed not to be a `Maybe` when deciding whether a `Maybe` of it writes
`null`.

## Tests

```sh
cd package && roc test ConformanceTest.roc && roc test TimeTest.roc
cd package && roc test Decode.roc && roc test Encode.roc && roc test Int.roc && roc test Streaming.roc && roc test Secret.roc && roc test Value.roc
cd package && roc test JsonValue.roc && roc test FromJson.roc && roc test ToJson.roc
cd examples/shop && roc test main.roc
cd schema-test && roc test main.roc
cd json-test && roc test main.roc
cd closure-test && roc test main.roc
```

`ConformanceTest.roc` is generated from `../test-suite` by
`scripts/gen_conformance.py`: for each valid file the values, the canonical
forms, the hash (`.hash`) and the stream reader giving the same values in chunks of any
size; for each invalid file a rejection with the code of its `.error`, also
by the stream reader, whose error positions after a byte order mark are the
whole-file parser's; and the check that `ErrorCode.roc` matches
`../spec/errors.haus` (after changing the catalogue, run
`python3 scripts/gen_error_codes.py`). `ErrorCode.roc`'s own tests run with
those of every module that imports it.
`TimeTest.roc` holds the same std/time cases as the TypeScript and Rust
bindings.

[`schema-test/`](schema-test) runs the schema conformance suite
(`../test-suite/schema`, spec §15): `scripts/gen_schema_conformance.py`
generates a module per schema with `haus-gen` (so it needs Rust) and
`SchemaTest.roc` with one `expect` per case (an `Err` case must fail with
its `code`). A schema with attributes also
gets a module generated without them (`AttributesBare.roc`), which must give
the same results (attributes don't matter, spec §15). Re-run it after changing
the suite or the generator:

```sh
python3 scripts/gen_schema_conformance.py
```

[`json-test/`](json-test) runs the JSON suite (`../test-suite/json`, spec §16)
the same way: `scripts/gen_json_conformance.py` generates `SchemaBased.roc`
for `schema-based.schema.haus` with `haus-gen roc --json`, a JSON module for
each schema of the schema suite (they only have to compile), and
`JsonTest.roc` with one `expect` per schema-based, self-describing and import
case (an `Err` case with its `code`) and per `valid/NAME.jsonl` (each a
self-describing case: an envelope per value of the file).
